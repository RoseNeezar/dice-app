Fix the layout regression first.

Several auditors independently reported that the camera, the viewer and the crop review render blank or collapsed. All of it traces to one cause: the old index.html had a <div id="root"> and the stylesheet gives #root its display:flex; flex-direction:column; height:100%. TanStack Start mounts into <body> instead, so screens that rely on a flex parent to claim the viewport get no height. Move those #root rules onto body in src/styles/global.css and re-check every screen. Most of the "UX & visual" findings below should disappear with it.

Auditor verdicts

Feature parity

Against the feature set a CamScanner user arrives with, OpenScan covers roughly 85% of it and covers most of it unusually well: capture (batch, ID card, book spread, QR, torch, zoom, auto-shutter, gallery import), edge detection with a genuinely good manual crop editor (auto re-detect, full page, reset, magnifier loupe, keyboard nudging), six scan looks plus brightness/contrast/saturation/detail/rotate/deskew applied non-destructively, full page editing (drag and keyboard reorder, split, merge, move, duplicate, retake, delete) and a complete annotation stack with undo/redo, folders/tags/stars/colours/trash/full-text search, and an export path (PDF with page size, orientation, margin, quality, watermark, password and an invisible OCR layer, plus JPEG, TXT, DOCX, CSV and ZIP) that is broader than most commercial competitors. The gaps are concentrated in three places. First, security and durability: the per-document lock is entirely inert — the app paints a padlock and says the document "needs the app passcode to open", and nothing ever checks the flag — while the whole library sits in never-persisted IndexedDB with no backup, export-all or import path of any kind, so a Safari 7-day eviction or a cleared site-data takes everything with no recovery. Second, text recognition is materially weaker than advertised: the "Read text automatically" toggle is wired to nothing, the "To Text" capture mode reads no text and raises a toast promising work that never happens, and OCR cannot run offline in any fresh session because tesseract's worker, core and language data are all fetched from a third-party CDN that the service worker does not cache — contradicting the README, the About text and the Settings hint. Third, two whole workflows are absent: PDFs cannot be imported (every input is accept="image/*"), so an existing document can never be signed, annotated or merged with a scan, and there is no print action anywhere despite an unused print glyph in the icon set.

Capture & crop

The capture pipeline's logic is largely sound — the still is re-detected in its own frame so the stored quad is in the right coordinate space, coverTransform correctly matches the video's object-fit: cover (including portrait-in-landscape), moveCorner genuinely prevents folded or out-of-frame quads, the crop quad is normalized and survives resize via ResizeObserver, and I verified empirically that Book mode yields two pages and ID Card composes both sides onto one A4-ish portrait page with the filter correctly forced to 'original'. The serious problems are around it: a dead #root CSS selector means the shell never fills the viewport, so the viewfinder is a 204 px strip with its close button buried under the mode strip and the review crop editor collapses to zero height and shows nothing at all; and the camera route has no session guard, so any reload leaves a screen that silently swallows every shot and cannot be exited. Beyond those, auto-capture re-fires on an unchanged scene every 2.2 s, the "To Text" mode and the "Read text automatically" setting never run OCR, and a camera that dies mid-session goes undetected and keeps saving its frozen last frame.

Library & annotations

The library/viewer/annotation stack is carefully built — the drag-to-reorder implementation is genuinely correct (pointer events with touch-action: none on the handle, scroll-compensated hit testing, autoscroll, and a commit that produces the right final order), the signature pad really does emit a transparent PNG trimmed to the ink, and collectGarbage correctly honours the signatures kv key that saveSignature writes. The serious defects are elsewhere: three of them are data-loss or privacy holes — eager deletion of shared annotation blobs destroys signatures still in use on other pages, the per-document \"Lock\" is enforced nowhere in the codebase, and redaction blacks out pixels while leaving the redacted words in the OCR layer that feeds search and the searchable PDF. Beyond those, page selection is completely unreachable on desktop, rotating a page silently displaces and distorts every annotation on it, split/move scramble page order, a stale global selection survives the hardware back button, and sorting by size is O(n²) in renders.

Export, OCR & security

The output pipeline is unusually well-built in its mechanics — I verified the RC4-128 security handler produces PDFs that qpdf opens with the right password and rejects without it, the ZIP writer's headers are byte-correct, the page-size/margin/fit maths never crops, PBKDF2 (210k, SHA-256, random 16-byte salt, constant-time compare) is textbook, and the service worker really does serve deep links offline. The defects are almost all in the layer above the maths: two security controls that the UI promises and the code does not implement (per-document Lock is read only to draw a padlock; redactions blacken the pixels but leave every redacted word in the PDF text layer and in the .txt/.docx/.csv exports), a searchable layer that silently vanishes for the ten non-Latin languages the app itself offers, OCR that reaches out to cdn.jsdelivr.net on every cold start while the screen says \"runs entirely on this device\", a Share button that loses its transient activation during the export and quietly becomes a download, and an autoOcr setting that nothing reads. I read every line of the files in scope, built and drove the app in a real browser, and verified the PDF, encryption, watermark and OCR findings against generated output rather than by inspection alone.

UX & visual

No. As shipped this does not look or feel like a product anyone would pay for, because it barely renders: TanStack Start puts the app straight into <body> while global.css styles a #root element that never exists, so every screen is only as tall as its content. Three screens whose children are all absolutely positioned therefore measure zero pixels and clip themselves away — the camera is a blank screen, the page viewer is a blank screen, and the crop review shows its buttons but not the photo you are meant to be cropping. Everything else works but feels wrong: headers scroll off, the scan FAB and the document toolbar are anchored to the bottom of the content rather than the window (on a 50-page document the Share button is seventeen rows below the fold), and the multi-select action bar opens off-screen. Underneath that one bug the design is genuinely good — the token system, the export sheet, the settings screen, the annotation and signature UI are all considered and well made in both themes — which is what makes the failure so frustrating: a one-line fix separates this from something that reads as a real CamScanner competitor. What survives that fix is a second tier of real problems: a camera-permission failure traps you on a screen whose only exit button is painted under the error overlay; modals have no focus trap, no focus restore and no scroll lock; hidden viewer chrome stays keyboard-focusable including a Delete that opens a destructive dialog; --text-3 fails WCAG AA across the whole light theme; and selection mode is mouse-unreachable, which makes restoring from the trash impossible on a desktop. The weakest screen is the crop review (src/screens/ReviewScreen.*): it is the one screen every single scan must pass through, it currently shows no image at all, its page-nav arrows sit on top of the crop edge handles and steal the drag (I dragged a handle and got sent to the previous page instead), its action bar clips "Delete" off the edge at 320px, and its "Done" is a 31px target. Judged as a whole, this is a beautiful design one commit away from being usable, and about six commits away from being shippable.

Accessibility & performance

The app is well-instrumented for accessibility in places (keyboard page reordering, keyboard crop handles, sr-only status regions, named icon buttons), but three structural problems undercut it: a stylesheet that targets a #root element the TanStack Start shell never creates, so every screen is mis-sized and the page viewer, the crop review pager and 78% of the camera render at zero height; a Slider primitive whose <label> binds to its reset button rather than its range input; and sheets/dialogs with no focus trap and no focus restore. On performance the CV engine itself is reasonable (detectDocument 108 ms, renderPage 470 ms on a 12 MP frame in Node on this machine) but it is shipped twice — once in the worker chunk and once in the 381 KB main entry chunk — and the app around it is not: boot eagerly hydrates every page row including full OCR word boxes (+81 MB heap, 388 ms → 1379 ms for a 1000-page library), opening a document issues 300–400 sequential IndexedDB blob reads just to print a byte count, the object-URL cache leaks and can revoke a URL a live <img> is showing, and batch capture blocks the shutter for the whole full-resolution render of the previous page.

Security & privacy

The obvious injection sinks are in good shape: there is no dangerouslySetInnerHTML or innerHTML anywhere, all user text reaches the DOM through React, the DOCX writer strips invalid XML and escapes the five entities, the ZIP writer rejects .. segments, suggestPdfName strips path separators, control characters and Windows device names, and toOpenableUrl correctly rejects everything that is not http(s) so a barcode cannot produce a tappable javascript: link. The passcode implementation is sound (PBKDF2-SHA256/210k, 16-byte WebCrypto salt, constant-time compare, current code required to change or remove it) and the PDF security handler faithfully follows ISO 32000-1 Algorithms 2/3/5 with the password never persisted. What is wrong is the gap between the app's promises and what it delivers: redaction is cosmetic in every export that carries the OCR layer, the per-document Lock does literally nothing while claiming to need the passcode, and OCR silently downloads and executes third-party JavaScript from cdn.jsdelivr.net inside the app's origin — with no CSP and no SRI — and then hands that code the scanned page images, which is also why the offline and "nothing leaves the device" claims do not hold.

Routing

The router migration itself is mostly sound — file routes match the store's Route union correctly, the camera's MediaStream tracks, rAF detection loop, OCR job, export job and annotation flush all stop cleanly on a route change (verified: tracks go to 'ended', rAF and worker traffic go to zero), the passcode gate holds against deep links, back and forward, and the service worker serves nested paths correctly offline. What the migration broke is everything that assumed the old, history-less world: the document shell lost its #root wrapper, which the entire CSS layout is built on, so every screen collapses to content height — the crop review renders a 0-pixel viewport with no page visible, and the camera's top-bar buttons are physically unclickable underneath the mode strip. The capture session still lives only in memory, so any URL entry into /doc/:id/camera (a reload or a phone's tab discard is enough) yields a viewfinder whose shutter silently stores nothing and whose close button is inert, and every abandoned camera visit leaves an empty ghost document behind. State that used to be cleared by the store's own navigation — the multi-select selection, the search query — now leaks across the system back gesture, and screens that take both a docId and a pageId never check that the two agree, so a stale viewer URL rotates or deletes a page in a different document than the one on screen.
